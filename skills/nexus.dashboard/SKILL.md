# nexus.dashboard — overview issue identity block + dashboard schema

TRIGGER when: setting up a new operator nexus and seeding the overview
issue `#1`; the working directory / host / repo provenance of a nexus
needs recording somewhere notable; the dashboard's content has drifted
between runs and needs a stable skeleton; reviewing or editing what
`ng dashboard put` pushes; `ng dashboard put|get|validate` warned that
the dashboard is over its size budget; an operator (or fresh
orchestrator) asks "where does this nexus live / how do I orient."

## The two rules

1. **Identity lives in `#1`, auto-generated.** The working directory
   and machine identity of a nexus belong in the overview issue body
   (`nexus:overview`, conventionally `#1`) — the one notable surface
   every operator sees — as an **auto-generated, delimited block**, not
   hand-typed prose. Generate it with `ng nexus-identity`.

2. **The dashboard has a fixed schema.** Every operator's dashboard
   uses the **same six sections**, scaffolded and validated by
   `ng dashboard scaffold` / `ng dashboard validate`. The section set is
   the single source of truth (`DASH_REQUIRED_SECTIONS` in `monitor/ng`)
   — change it there and it propagates to every nexus on the next
   `nexus-code` pull.

Both are **standard across all operator nexuses.** They are derived
entirely from each nexus's own environment/config (`$NEXUS_ROOT`,
`github.repo`, hostname, the watcher pidfile/log paths) — nothing is
hardcoded to one operator — so a second operator running the same code
gets their own correct identity block and conforming dashboard with
zero edits.

## Identity block — `ng nexus-identity`

```
ng nexus-identity --dry-run          # render to stdout, no GitHub write
ng nexus-identity --upsert-overview  # idempotently PATCH the block into #1
```

The block is bounded by `<!-- nexus-identity:start -->` /
`<!-- nexus-identity:end -->` and is upserted in place (replace, never
duplicate) — exactly the precedent set by `ng interactive-sessions`.
Repeated runs converge; it can't drift. The bot identity (installation
token, REST PATCH) is used for the write.

Fields, all **derived** (nothing hardcodes `<operator>`):

| Field | Source |
|-------|--------|
| **Working directory** (headline) | `$NEXUS_ROOT`, else script-relative root |
| Host | `hostname` |
| Asset + issue repo | `github.repo` + overview issue number |
| Implementation clone | the nexus root's git `origin` remote + current branch |
| Watcher pidfile / log | `<root>/monitor/.state/watcher.{pid,log}` |

It is **identity, not status** — a stable "where things live" record.
Live status (what's running, what's blocked) is the dashboard's job,
below it in the same issue body. The block ends with a one-line
orient/resume pointer (cockpit `monitor/svc.sh`, dashboard location,
reports dir) and a "do not edit by hand — auto-generated" note.

Who runs it: the **orchestrator**, from the primary clone, after a
fresh setup or whenever the root/host/repo provenance changes (rare).
It's cheap and idempotent, so re-running it to repair drift is safe.

## Dashboard schema — `ng dashboard scaffold | validate | put`

The dashboard is the content **between** the
`<!-- NEXUS_DASHBOARD_START/END -->` markers in `#1`. It must carry
these six H2 sections, in this order:

| Section | Populated by |
|---------|--------------|
| `## Identity` | **Pointer** to the `ng nexus-identity` block above — never a copy (single source of truth). The generated block's own `## Nexus Identity` heading also satisfies this slot (`#886`), so `ng nexus-identity > body.md` + the other five sections validates clean |
| `## Infra` | Operator-narrated: watcher / orchestrator / CC-pin health |
| `## Services` | Auto-populatable from `monitor/services.registry` (name + healthcheck); narrate exceptions |
| `## In-flight` | Active worker windows (mirrors `tmux list-windows` + heartbeats). **Live windows ONLY** — see below |
| `## Awaiting operator` | Threads/decisions blocked on the operator |
| `## Recent landings` | Last few merged PRs / completed tasks |

Verbs:

```
ng dashboard scaffold                 # print the canonical skeleton (hints inline)
ng dashboard get --stat               # size breakdown only, never the body (agent-safe)
ng dashboard validate                 # strict, on the LIVE dashboard (the default; #958)
ng dashboard validate [--body-file P|-]  # a candidate; exit 1 if a required section is
                                      #   missing OR DUPLICATED (#1058),
                                      #   or OVER the DASH_MAX_* size budget. `-` = stdin.
ng dashboard put --body-file P        # splice + PATCH, then READ BACK to prove it landed
                                      #   (#1118). Refuses: a body containing a marker
                                      #   (#959), a live body without exactly ONE marker
                                      #   pair, anything over GitHub's 262144-byte cap.
                                      #   rc 4 = could not verify != failed. Cache and
                                      #   freshness stamp only after verification.
                                      #   WARNS on missing sections and on the size
                                      #   budget; never blocks.
ng dashboard get                      # fetch the current dashboard middle
ng dashboard get --stat               # size breakdown ONLY — never the body
```

- **`scaffold`** emits the skeleton with a one-line hint per section.
  Seed a new dashboard by piping it into `put`, or use it to remember
  the section set.
- **`validate`** is the **strict gate** (exit 1 on drift) — for CI /
  pre-commit / a deliberate conformance check. It checks both axes:
  required sections present, and within the size budget below.
- **`put`** runs the same checks in **warn-only** mode: it prints what
  is missing or oversized to stderr but still pushes. Rationale: the
  operator must be able to update the dashboard in a hurry; a hard
  block there would be a footgun. Use `validate` when you want the
  hard failure.
- **`get --stat`** is what an agent should reach for. Plain `get` dumps
  the whole body to stdout, which is fine for a healthy dashboard and a
  context blowout for a sick one. `--stat` reports total bytes,
  per-section bytes/lines/entry counts and the largest single entry, and
  writes the body to `.state/dashboard.md` so you can read it
  deliberately if you still need it.

## The dashboard is size-bounded — it is a surface, not a log

The dashboard is a **glanceable status surface**. It answers "what is
true right now," and every section is a REPLACE, never an APPEND.

The failure this rule exists to prevent, observed 2026-08-03: the
dashboard reached **213,381 bytes across 195 lines**, `## In-flight`
alone at **166 KB / 115 entries** with single entries up to **9.3 KB** —
while exactly **3 worker windows were live**. Successive orchestrators
prepended session narrative and never pruned. Nothing checked the size
at write time, so nothing stopped it, and the surface the operator
depends on became unreadable.

Two rules follow, and they are the ones to hold:

1. **`## In-flight` mirrors LIVE worker windows only.** Reconcile it
   against `tmux list-windows` on every update and DELETE rows for
   windows that no longer exist. A window that has wrapped up leaves the
   section — it does not accumulate there.
2. **Narrative history belongs in `reports/`, not the dashboard.** If
   what you are about to add is a record of what happened, it goes in a
   report (`ng report-init <slug>`); the dashboard gets at most a
   one-line link. `## Recent landings` keeps the most recent handful.

`monitor/ng` enforces this at write time via the `DASH_MAX_*` constants
next to `DASH_REQUIRED_SECTIONS` — total bytes, per-section bytes, entries
per section, and bytes per entry. Breaching any of them prints the numbers
**and the remedy**; `validate` fails hard, `put` and `get` warn loudly.
Retune the thresholds in that one place. Before pruning an oversized
dashboard, archive the old body so nothing is lost:

```
ng dashboard get > /tmp/dashboard-archive.md
ng upload /tmp/dashboard-archive.md --repo-path general/dashboard-archive-<date>.md
```

**`put --body-file` takes SECTIONS-ONLY — never the whole fetched body.**
`put` splices `<f>` *between* the issue's `NEXUS_DASHBOARD_START/END`
markers, preserving the intro + markers and replacing only the content
between them. So `<f>` must be the six `##` sections alone — no intro, no
`NEXUS_DASHBOARD_*` markers. **The trap:** fetching the current body
(`gh api …/issues/1 --jq .body`), editing it, and passing that whole
thing back to `put` nests the entire body (intro + markers + content)
*inside* the markers, one level deeper per `put` — a real overview `#1`
accumulated **8 nested marker pairs** (~4100 lines) this way. For routine
updates keep a sections-only file and `put` that. If a body already has
multiple marker pairs, do **not** `put` it — extract the intro (everything
before the first `NEXUS_DASHBOARD_START`), append one clean marker pair
wrapping fresh sections-only content, and PATCH wholesale
(`jq -Rs '{body:.}' | gh api -X PATCH …/issues/1 --input -`); verify
`grep -c NEXUS_DASHBOARD_START` on the live body `== 1` and
`ng dashboard validate`.

## Presence is not uniqueness

The dashboard verbs' recurring defect is a check that answers a WEAKER
question than the one it reports on. `put`'s precondition asserted the
markers were PRESENT and never that they were UNIQUE — the same sentence
`#1058` writes about `validate` and section headings. A body carrying two
`NEXUS_DASHBOARD_END` markers passed it and then silently no-oped: rc 0, URL
printed, stderr empty, body unchanged. Measured at 198,236 bytes, 64 KB UNDER
GitHub's cap, so size was not the cause.

Two habits follow, and they are the whole skill:

1. **Exactly one.** One START, one END, one of each required section. Ask it
   at every entry point — `get`, `put` and `validate` — because whichever one
   you skip is the one that hands the next verb a corrupt body. `get` matters
   most: it produces what `put` consumes, so a bad `get` arms the next
   round-trip.
2. **Prove the write with an INDEPENDENT GET, not with the PATCH response.**
   A 200 is not evidence — and neither is the response body. Measured on
   scratch issue `<your-org>/nexus-code#1128`: an over-cap PATCH returns 200
   whose `.body` is **the body you sent**, while the store keeps the old one
   (`response_echoed_sent = YES` in every case, swallows included; the limit is
   262,144 **bytes**, and 262,144 lands while 262,145 swallows). A check
   comparing against that response compares the request with itself — its
   true-positive set for a swallow is empty. This PR shipped exactly that
   mistake and six tests "proved" it worked against a mock that had the forge
   backwards. Only a separate GET observes the store.

   Do NOT reconcile byte counts instead: size is a proxy that drifts.

If a dashboard genuinely reaches the cap, `put` REFUSES and says by how much,
splitting the total into the dashboard region and the prose outside it — so
you can see whether trimming the dashboard can even help. It does not
auto-trim: what to drop is editorial judgement, and a publish verb that
quietly publishes something other than what it was handed is the same defect
wearing better clothes.

## Consistency with the rest of the nexus

- The identity block is **metadata, not content** — it does not
  violate the overview "routing-only" rule (`CLAUDE.md`). Per-task
  back-and-forth still belongs in dedicated issues; the identity block
  and dashboard are the standing skeleton of `#1`, not discussion.
- The schema-enforcement pattern mirrors `nexus.report`'s
  `ng report-check`: a canonical section list, a checker, a scaffold.
- Spawning, wrap-ups, and routing are unchanged — see
  `nexus.tmux-spawn`, `nexus.report`, `nexus.bot`.

## Where the schema lives (for maintainers)

`monitor/ng`: `DASH_REQUIRED_SECTIONS` (the section array),
`DASH_SECTION_ALIASES` (headings that also satisfy a required section),
`DASH_MAX_*` (the size budget — total / per-section / entries / per-entry,
all in one block beside the section array),
`IDENTITY_HEADING` (the identity block's H2, declared once and consumed
by the generator, the scaffold's pointer prose and the validator),
`_dashboard_template` (scaffold), `_dashboard_missing_sections` and
`_dashboard_oversize_report` (the checkers shared by `validate` and the
`put`/`get` warn paths), `_dashboard_oversize_advice` (the remedy text
every breach prints), `_dashboard_stats_tsv` + `_dashboard_stat_render`
(the `get --stat` breakdown), and `cmd_nexus_identity`
(the identity generator + idempotent upsert). Tests:
`monitor/watcher/test-ng-dashboard.sh` (scaffold + validate + put-warn +
the size budget, one fixture per `DASH_MAX_*` rule),
`monitor/watcher/test-ng-nexus-identity.sh` (identity render +
idempotent upsert), and
`monitor/watcher/test-ng-identity-dashboard-sync.sh` — the cross-check
(`#886`): the validator consumes the generator's output, and renaming
`IDENTITY_HEADING` must move all three consumers together. **A generator
and its validator have to be checked against EACH OTHER**, not
separately; each was individually correct here and the pair was not.
